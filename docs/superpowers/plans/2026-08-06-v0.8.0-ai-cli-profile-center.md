# UCLI 0.8.0 AI CLI 配置档案中心 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Follow the checkbox order, keep each change test-first, and stop at the review checkpoints.

**Goal:** 把 UCLI 从“会话编排器”升级为“会话编排器 + AI CLI 配置档案中心”。0.8.0 首期完整支持 Codex 配置档案，并为 Claude Code、OpenCode、U-Code 提供统一的已安装状态入口和后续适配扩展点。

**Architecture:** UCLI 不接管 CC Switch 数据库，不修改 Codex 的 `config.toml` 或 `auth.json`，也不启动协议转换代理。UCLI 在 SQLite 中保存非敏感档案元数据，在 Electron `safeStorage` 中加密保存 API Key，并把每个可管理 Codex 档案投影为 `$CODEX_HOME/ucli-<id>.config.toml`。启动 UCLI 会话时使用 Codex 官方 `--profile <name>` 选择档案，密钥只通过该 PTY 进程的环境变量注入。项目默认、应用默认和会话显式选择在 UCLI 内解析；运行中的会话不自动重启。

**Tech Stack:** Electron 32、Vue 3、Pinia、Ant Design Vue 4、Node.js ESM、node-pty、sql.js、`smol-toml@1.4.2`、Electron `safeStorage`、Node test runner、electron-vite、electron-builder。

## 1. 产品定义

### 1.1 0.8.0 做成什么样

新增一级导航“配置档案”。页面不是一个 API Key 表格，而是以 AI CLI 为入口的配置工作区：

```text
┌ 配置档案 ─────────────────────────────────────────────────────┐
│ [Codex · 可管理] [Claude Code · 沿用系统] [OpenCode · 沿用系统] │
│ [U-Code · 沿用系统]                                           │
├───────────────────────────────────────────────────────────────┤
│ Codex 状态                                                     │
│ 已安装  ·  当前系统 Provider: work_gateway  ·  配置目录 ...     │
│                                                               │
│ [＋ 新建档案] [从现有 Provider 创建引用档案]                    │
│                                                               │
│ ┌ 公司网关 ─────────────┐  ┌ 官方配置 ────────────────┐        │
│ │ 自建 · api.example.com │  │ 跟随 Codex 当前配置       │        │
│ │ gpt-5.x · high         │  │ 当前 Provider: openai    │        │
│ │ 应用默认               │  │                          │        │
│ │ 编辑  设为项目默认 ... │  │ 设为默认                 │        │
│ └────────────────────────┘  └──────────────────────────┘        │
└───────────────────────────────────────────────────────────────┘
```

用户在新建 Codex 会话时可以选择：

- “按项目默认”；
- “按 UCLI 默认”；
- “跟随 Codex 当前配置”；
- 某个具体配置档案。

恢复历史 Codex 会话时仍默认保持 0.7.x 的“来源 Provider”行为。只有用户显式选择档案时，才覆盖恢复策略。

运行中的会话切换档案后显示“重启后生效”，并提供明确的“立即重启”按钮；UCLI 不自动终止进程。

### 1.2 档案类型

0.8.0 支持三类 Codex 档案：

1. **系统当前（虚拟档案）**：不写数据库、不传 `--profile`，继续跟随 `config.toml` 和 CC Switch 的实时切换。
2. **引用档案**：引用 `config.toml` 已存在的 Provider，只在 UCLI 管理的 profile 文件中保存 Provider ID、模型、推理强度和上下文窗口；不复制第三方 Provider 的完整配置或密钥。
3. **托管档案**：由 UCLI 保存名称、Base URL、模型、推理强度、上下文窗口和加密密钥，并生成独立的 Codex profile 文件。

### 1.3 配置优先级

新会话使用以下确定性顺序：

```text
新建对话框显式选择
  > 项目默认档案
  > UCLI 应用默认档案
  > 系统当前（不传 --profile）
```

导入/恢复会话使用以下顺序：

```text
导入对话框显式选择档案
  > 历史来源 Provider（0.7.x 既有行为）
  > 当前系统 Provider 回退（来源已不存在时）
```

项目默认和 UCLI 默认不会静默覆盖历史会话的来源 Provider。

### 1.4 与 CC Switch 的结合边界

吸收的产品模式：

- 按 AI CLI 分组的配置入口；
- Provider 卡片式管理；
- 从现有配置建立引用；
- 修改前版本快照、漂移检测和回滚；
- 切换后明确提示受影响的运行会话。

不复制的能力：

- 不读取或写入 `~/.cc-switch/cc-switch.db`；
- 不做本地反向代理、协议转换、测速、熔断或自动故障转移；
- 不管理 OAuth/ChatGPT 登录态，不读取或写入 `auth.json`；
- 不同步 MCP、Skills、Prompt；
- 不改写 Codex rollout、会话索引或历史 Provider；
- 不覆盖用户或 CC Switch 管理的 `config.toml`；
- 不把 API Key 放入 TOML、命令行参数、日志、诊断报告或 Renderer 状态。

| --- | --- | --- |

## 2. 安全与兼容约束

- Codex 官方配置档案位于 `$CODEX_HOME/<profile-name>.config.toml`，通过 `--profile <profile-name>` 选择。UCLI 只创建文件名匹配 `ucli-[a-f0-9]{32}.config.toml` 的文件。
- UCLI 管理的文件首行带非敏感标记 `# ucli-profile-id: <uuid>`；删除、覆盖、恢复前必须同时验证文件名、标记和数据库记录。
- `config.toml`、`auth.json`、用户创建的 `*.config.toml` 永远只读。
- 托管档案固定使用 Codex 当前支持的 Responses wire API；0.8.0 不提供 Chat Completions/Anthropic 协议选择器。
- 外部 HTTPS Base URL 可以保存；HTTP 只允许 `localhost`、`127.0.0.1`、`::1`。拒绝嵌入用户名/密码、控制字符和非 HTTP(S) URL。
- API Key 只能在 Electron main process 解密，并仅合并到目标 Codex PTY 的 `env`。Renderer 只收到 `hasSecret` 和可选的末尾四位掩码，不收到明文或密文。
- `safeStorage.isEncryptionAvailable()` 为 false 时，不允许保存新的密钥，也不允许明文降级；引用档案和无密钥本地 Provider 仍可使用。
- 档案文件写入采用同目录临时文件 + 原子替换。更新前校验 SHA-256；哈希不一致时标记 `drifted`，不覆盖外部修改。
- 每个档案保留最近 10 个非敏感版本快照。回滚配置不回滚密钥。
- 运行中的 PTY 不自动重启。切换档案只保存“期望档案”，当前 PTY 继续展示“实际档案”，直到用户重启。
- 删除仍被默认绑定、会话引用或运行中使用的档案时返回 `PROFILE_IN_USE`，UI 必须先让用户替换绑定。
- Renderer IPC 返回值必须经过白名单构造，不能直接返回数据库行、TOML parse object、环境变量或异常堆栈。
- Windows 10+ 与 macOS 12+ 都是发布门槛；路径规范化、大小写比较和原子替换必须有平台测试。
- 0.7.x 的 `source/live/explicit` Provider 策略继续存在。`profileId` 是正交字段，不把旧数据迁移成伪档案。

## 3. 数据模型与接口

### 3.1 SQLite 迁移

在 `electron/persistence/db.js` 增加：

```sql
CREATE TABLE IF NOT EXISTS ai_cli_profiles (
  id                  TEXT PRIMARY KEY,
  adapter_id          TEXT NOT NULL,
  name                TEXT NOT NULL,
  kind                TEXT NOT NULL,
  native_profile_name TEXT UNIQUE,
  provider_id         TEXT,
  base_url            TEXT,
  model               TEXT,
  reasoning_effort    TEXT,
  context_window      INTEGER,
  config_json         TEXT NOT NULL DEFAULT '{}',
  has_secret_hint     INTEGER NOT NULL DEFAULT 0,
  file_sha256         TEXT,
  created_at          INTEGER NOT NULL,
  updated_at          INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS ai_cli_profile_bindings (
  scope_type TEXT NOT NULL,
  scope_key  TEXT NOT NULL,
  adapter_id TEXT NOT NULL,
  profile_id TEXT,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (scope_type, scope_key, adapter_id)
);

CREATE TABLE IF NOT EXISTS ai_cli_profile_revisions (
  id          TEXT PRIMARY KEY,
  profile_id  TEXT NOT NULL,
  config_json TEXT NOT NULL,
  file_sha256 TEXT,
  reason      TEXT NOT NULL,
  created_at  INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS ai_cli_profile_secrets (
  profile_id TEXT PRIMARY KEY,
  ciphertext TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

向 `sessions` 添加：

```sql
ALTER TABLE sessions ADD COLUMN profile_id TEXT;
```

约束由 service 层执行：

- `adapter_id` 在 0.8.0 只接受 `codex`；
- `kind` 只接受 `reference`、`managed`；
- `scope_type` 只接受 `app`、`project`；
- `scope_key` 在应用默认时固定为 `*`，项目默认时使用规范化绝对路径；
- 删除档案前显式查询引用，不依赖 SQLite 外键级联。

### 3.4 会话运行态

会话摘要增加：

```js
{
  profileId,          // 下次启动期望使用的档案
  activeProfileId,    // 当前 PTY 实际使用的档案
  pendingProfileId,   // 运行中切换后等待重启的档案
  profileStatus,
  restartRequired
}
```

Codex 启动参数规则：

- `profileId === null`：保留 0.7.x `source/live/explicit` 解析和 `-c model_provider=...` 行为；
- `profileId !== null`：追加 `--profile <nativeProfileName>`，不再追加旧的 Provider override；
- `--profile` 等全局参数放在 `resume` 子命令之前，避免不同 Codex 版本的参数解析差异；
- `session.model` 只有在没有档案模型时才追加 `--model`，避免出现两个来源；
- 档案密钥只加入本次 PTY 的 `env`；
- profile 文件缺失、漂移未确认、引用 Provider 缺失或密钥无法解密时阻止启动并返回稳定错误码。

## 7. 验收定义

0.8.0 完成必须同时满足：

- 用户可以在独立一级页面创建、编辑、复制、删除和回滚 Codex 档案；
- 用户可以设置 UCLI 默认和项目默认，并在单个会话上覆盖；
- 同一工作台的不同 Codex 分屏可以使用不同档案；
- 重启 UCLI 后工作台、会话和档案绑定一致恢复；
- 历史会话恢复规则不被项目默认破坏；
- CC Switch 可继续自由修改 `config.toml`，UCLI 不覆盖它；
- 托管密钥只存在于 OS 加密存储和目标 PTY 内存环境中；
- 档案文件被外部修改或本地 DB 丢失时有可解释、可修复状态；
- Claude Code、OpenCode、U-Code 的入口准确显示“沿用系统配置”，不承诺 0.8.0 未实现的能力；
- 全量测试、构建、发布验证、Windows 安装和 macOS 构建全部通过。

- CC Switch 官方仓库与发布说明用于提炼 Provider 卡片、配置备份和多 CLI 入口模式；UCLI 不读取其内部数据库，也不复制代理接管能力。<https://github.com/farion1231/cc-switch>
