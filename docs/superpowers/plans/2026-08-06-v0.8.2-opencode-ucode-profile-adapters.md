# UCLI 0.8.2 OpenCode 与 U-Code 配置档案适配器 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 0.8.0/0.8.1 配置档案框架中完整接入 OpenCode 与 U-Code，让每个项目和分屏可以选择独立的 Provider、模型、轻量模型和加密 API Key，同时保持 UCLI 权限规则的最高会话优先级。

**Architecture:** OpenCode 与 U-Code 共用现有 `OpenCodeAdapter` 运行时框架，但各自注册独立 ProfileAdapter。档案不写入全局或项目 JSON/JSONC，也不写两个 CLI 的 auth 文件；main process 把档案编译为白名单 inline config，和 UCLI permission config 合并后分别注入 `OPENCODE_CONFIG_CONTENT` 或 `UCODE_CONFIG_CONTENT`。API Key 在 inline config 中只出现 `{env:UCLI_*_PROFILE_*}` 引用，真实值只进入目标 PTY 环境。

**Tech Stack:** Electron 32、Vue 3、Pinia、Ant Design Vue 4、Node.js ESM、node-pty、sql.js、Electron `safeStorage`、Node test runner、electron-vite、electron-builder。

## Global Constraints

- 开始前 0.8.0 通用 profile 框架和 0.8.1 adapter registry 必须完成并通过验收。
- 版本固定为 `0.8.2`；OpenCode 和 U-Code 同版本交付，因为 U-Code 已通过 runtime profile 复用 `OpenCodeAdapter`。
- 两者必须使用独立 ProfileAdapter 和配置编译器；不得假设 U-Code schema 永远等于 OpenCode schema。
- 不修改 OpenCode 的 `~/.config/opencode/opencode.json/jsonc`、项目 `opencode.json/jsonc`、`.opencode/` 或 `~/.local/share/opencode/auth.json`。
- 不修改 U-Code 的 `~/.config/ucode/ucode.json/jsonc`、项目 `.ucode/ucode.json/jsonc`、state model 文件或登录数据。
- 不读取、迁移或重写 OpenCode/U-Code OAuth token、auth.json、Xiaomi MiMo 登录态、Codex 登录态或 Claude Code 导入凭据。
- “系统当前”档案只注入 UCLI permission config，继续让 CLI 自己合并 remote/global/project/auth 配置。
- 具体档案使用 runtime inline config。OpenCode 注入 `OPENCODE_CONFIG_CONTENT`；U-Code 注入 `UCODE_CONFIG_CONTENT`；不得互相设置另一方变量。
- UCLI permission 必须在 profile config 之后合并并覆盖整个 `permission` key。档案不得包含 `permission`、`tools`、`mcp`、`plugin`、`instructions`、`command`、`agent` 或任意 JSON 编辑器。
- API Key 只通过专用环境变量注入；inline config 只保存 `{env:VARIABLE_NAME}`。不得把 key 写进 JSON、argv、日志、诊断或 Renderer。
- 0.8.2 不调用 `/connect`、`auth login`、`auth logout`，不模拟交互式登录。
- 模型本地验证只能运行 `opencode models <provider>` 或 `ucode models <provider>`，不得加 `--refresh`，不得发送付费推理请求。
- 外部 Base URL 必须 HTTPS；HTTP 只允许 loopback。U-Code 明确保留用户输入 URL，不自动添加或删除 `/v1`。
- OpenCode 托管档案支持 OpenAI-compatible Chat Completions 与 Responses；U-Code 额外支持 Anthropic Messages。
- 不根据模型名称猜测 wire protocol、context/output limit、reasoning、modalities 或价格。
- OpenCode 的轻量模型编译为 `small_model`；U-Code 的轻量模型编译为 `model_groups.lite`，不得在新 U-Code 档案中写 `small_model`。
- U-Code 上下文预算只降低 compaction trigger，不伪造模型真实窗口；编译为 `compaction.max_context` 的精确模型映射。
- 恢复历史会话默认继续使用来源 session 的模型；只有用户显式选择档案才追加 `--model` 覆盖。
- 运行中的 PTY 不自动重启；desired/active/pending 行为与 Codex/Claude 一致。
- Windows 10+ 与 macOS 12+ 为发布门槛；继续使用现有安全 executable/shim resolver，不回退到 shell 字符串执行。
- 所有行为变更采用 TDD；每个任务先看到目标测试失败再实现。

## 产品结果

配置中心增加两个可管理页签：

```text
OpenCode                              U-Code
[系统当前]                            [MiMo 登录态 / 系统当前]
[公司 OpenAI 网关]                    [公司 OpenAI 网关]
[现有 anthropic/claude-sonnet]        [Anthropic Messages 网关]

主模型      provider/model            主模型      provider/model
轻量模型    small_model               轻量模型    model_groups.lite
上下文预算  不提供                     上下文预算  200K / 50% / 关闭
```

档案分两类：

1. `reference`：只选择 CLI 当前配置中已经存在的 `provider/model`；UCLI 不复制其 endpoint 或凭据。
2. `managed`：UCLI 创建仅对本会话有效的 provider definition、model selection 和加密 API Key。

托管协议：

| runtime | UI 选项 | 编译 `npm` |
| --- | --- | --- |
| OpenCode | OpenAI Chat Completions compatible | `@ai-sdk/openai-compatible` |
| OpenCode | OpenAI Responses compatible | `@ai-sdk/openai` |
| U-Code | OpenAI compatible | `@ai-sdk/openai-compatible` |
| U-Code | Anthropic Messages compatible | `@ai-sdk/anthropic` |

## 验收定义

- OpenCode 与 U-Code 都可以创建 reference/managed 档案并按应用、项目、会话绑定；
- 同一工作台中的不同分屏可以使用不同 Provider、模型和密钥；
- OpenCode 与 U-Code inline config、client env 和 secret env 完全隔离；
- UCLI permission 永远覆盖档案中的同名配置，档案不能配置任意工具/MCP/plugin；
- 托管 API Key 只存在于 OS 加密存储和目标 PTY 环境；
- OpenCode/U-Code 的全局、项目、auth、state 文件均未被修改；
- U-Code 的 Anthropic 协议、model groups 和 context budget 使用自身 schema，不由 OpenCode compiler 代替；
- 历史恢复、Gateway、统计、安装检测、分屏恢复无回归；
- 全量测试、Windows 安装包和 macOS 构建通过。
