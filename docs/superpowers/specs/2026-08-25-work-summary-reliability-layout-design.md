# 工作总结生成可靠性与页面布局重构设计

- 日期：2026-08-25
- 状态：待用户复核
- 关联决策：`docs/adr/0003-summary-reports-are-the-canonical-work-summary.md`

## 背景

真实 Claude 验收已经证明交互式生命周期可以完成指令投递、原生会话绑定和报告文件写入，但最新两次任务仍以 `SUMMARY_ARTIFACT_INVALID` 失败。模型输出包含完整正文和六个必需章节，却把六个并列章节都写成一级标题；当前校验器要求“摘要”为一级标题、其余章节为二级标题，因此整份报告被拒绝。

工作总结页面也在现有 7/17 固定栅格中不断增加任务元数据、状态、版本和管理操作。任务卡在狭窄左栏平铺多个按钮，当前周期版本又在同一栏重复显示，详情操作栏和三列元数据缺少响应式边界，形成明显的拥挤、重复和溢出问题。

## 目标

- 在不增加模型调用的前提下，把语义完整、仅标题层级不同的安全 Markdown 确定性规范化为现有规范格式。
- 不放宽凭据、绝对路径、HTML、文件边界、缺失章节、重复章节和章节顺序等安全要求。
- 失败时向用户显示具体且安全的原因，不再把所有错误压缩为“请重试”。
- 将工作总结页面重构为清晰的任务列表与报告详情主从布局。
- 在窄窗口下自动堆叠，操作按钮不挤压标题和正文。
- 保持 `summary_reports` 为唯一业务真相源，保持已有编辑、删除、重试、版本和实时状态语义。

## 非目标

- 不调用模型执行格式修复，不增加自动重试次数或隐藏的模型成本。
- 不允许模型缺失、重排或重复六个必需章节。
- 不放宽 Markdown 安全校验，不允许原始 HTML、凭据或本地路径进入数据库和 renderer。
- 不修改旧报告正文，不执行数据库批量迁移。
- 不重写工作总结生成状态机、会话删除事务或调度逻辑。
- 不增加 Markdown 正文编辑能力。

## 方案选择

采用“安全检查 → 确定性规范化 → 再校验 → 原子提交”的单次本地流程。

没有采用以下方案：

- **模型二次修复**：增加成本和等待时间，仍然具有格式不确定性。
- **直接放宽标题层级校验**：会让数据库中的所谓规范 Markdown 保留多种结构，继续扩大后续渲染和导出的兼容面。
- **立即迁移为全新文档标题结构**：长期可以统一为 `# 工作总结` 加六个二级章节，但本次会扩大旧管线、旧报告和导出兼容范围，不是关闭当前失败所需的最小改动。

页面采用“紧凑任务栏 + 弹性详情区”的 CSS Grid 主从布局。任务列表继续展示每个可管理的报告版本，版本历史移到右侧详情上下文，不再在左栏重复堆叠。高频操作保留在详情区，任务卡只保留选择、状态和一个紧凑操作入口。

## 规范 Markdown 结构

数据库和完成 workspace 中的新交互式报告继续使用当前规范：

```markdown
# 摘要
## 使用量分析
## 项目进展
## 跨项目观察
## 下一步建议
## 数据覆盖
```

规范化器只接受以下输入条件：

- 六个标题文本必须完全匹配且严格按上述顺序出现。
- 每个必需标题只能出现一次，且必须是 Markdown 文档根层的 ATX 标题。
- 必需标题的输入级别只能是一级或二级。
- 围栏代码、引用、列表、HTML 和注释中的相同文本不算章节标题。
- 章节内的其他标题允许存在，但必须保持相对层级。

规范化时，每个必需标题被改写为目标级别。该章节内直到下一个必需标题之前的子标题按相同层级差整体平移；如果平移会产生低于一级或高于六级的标题，则拒绝产物。正文、列表、代码块、链接和空白内容不做语义改写。

例如模型输出：

```markdown
# 项目进展
## 项目 A
### 已完成
```

规范化后为：

```markdown
## 项目进展
### 项目 A
#### 已完成
```

## 生成数据流

1. 模型继续只写 `output/report.md`。
2. `waitForCanonicalMarkdown()` 等待文件稳定，并先执行现有 UTF-8、大小、路径、HTML、凭据和本地路径安全检查。
3. 新的纯函数 `canonicalizeInteractiveSummaryMarkdown(markdown)` 使用 Markdown token 的源行映射识别真实标题，返回 `{ markdown, changed }`；无法确定性转换时抛出 `SUMMARY_ARTIFACT_INVALID`。
4. 规范化结果再次执行完整安全检查和严格标题顺序校验。
5. 如果 `changed` 为 true，job 通过受控 `workspaceService.writeArtifact(reportId, 'output/report.md', markdown)` 原子替换规范文件。
6. bytes 和 SHA-256 均从规范化后的 UTF-8 内容计算，数据库 Markdown、hash 和完成 workspace 保持一致。
7. 完成事务和后续 HTML/Markdown 导出继续使用数据库中的规范 Markdown，不增加任何模型调用。

## 错误呈现

主进程继续只持久化白名单错误码。renderer 增加共享安全错误映射：

- `SUMMARY_ARTIFACT_INVALID`：报告已生成，但内容结构或安全校验未通过。
- `SUMMARY_ARTIFACT_MISSING`：AI CLI 未写出报告文件。
- `SUMMARY_TURN_NOT_CONFIRMED`：生成指令未确认送达 AI CLI。
- `SUMMARY_RUN_TIMEOUT`：生成超过允许时间。
- 其他白名单错误显示对应安全文案，未知值回退为“工作总结生成失败”。

失败任务卡显示简短原因；详情显示可操作说明和安全错误码。不得显示 prompt、transcript、原始 Provider 输出或本地路径。

## 页面信息架构

### 桌面布局

- 页面顶部为标题、说明、刷新和“生成总结”主操作。
- 主内容使用两列 CSS Grid：左栏 `minmax(300px, 360px)`，右栏 `minmax(0, 1fr)`。
- 左栏独立滚动，展示全部可管理任务版本；标题最多两行，备注最多两行。
- 任务卡只直接展示标题、版本、当前标记、状态、时间和 CLI。
- “重试”在失败状态下作为唯一直接操作；编辑、查看对话和删除放入“更多”菜单。
- 右栏顶部展示报告标题、状态和主操作，下面依次为错误/进度、元数据、版本历史和 Markdown 正文。
- 版本历史从左栏移到右栏，作为当前报告周期的上下文，不再与任务列表纵向重复。

### 窄窗口

- 宽度小于 960px 时主内容改为单列，任务列表位于报告详情上方。
- 任务列表在单列模式下限制最大高度，避免把正文推到页面底部。
- 详情操作栏使用 `flex-wrap`，危险操作与导出操作保持可辨识间距。
- 元数据 descriptions 在桌面显示三列，在中等窗口显示两列，在窄窗口显示一列。
- Markdown 表格放入可横向滚动的内容边界，代码块继续独立滚动。

## 组件边界

- `electron/summaries/summaryMarkdownCanonicalizer.js`：纯 Markdown 标题识别和规范化，不读写文件。
- `electron/summaries/interactiveSummaryArtifact.js`：安全读取、调用规范化器、再次校验并返回规范内容及 `changed`。
- `electron/summaries/interactiveSummaryJobService.js`：仅在 `changed` 时通过 workspace service 原子写回，再执行现有完成事务。
- `shared/summaryTaskContracts.js`：状态与安全错误展示映射，main 和 renderer 都不接触原始错误文本。
- `WorkSummaryPanel.vue`：页面级主从布局和响应式容器。
- `SummaryReportListItem.vue`：紧凑任务卡及状态相关操作入口。
- `SummaryReportView.vue`：详情头、进度/错误、操作和 Markdown 内容。
- `SummaryHistory.vue`：右侧上下文中的紧凑版本切换，不再承担任务卡管理入口。

## 测试策略

### Markdown RED→GREEN

- 全部六节为一级标题时，规范化为当前 canonical 层级。
- 全部六节为二级标题时，“摘要”提升为一级，其他章节保持二级。
- 项目和小节标题随所属章节保持相对层级。
- canonical 输入字节保持不变，`changed` 为 false。
- 缺失、重复、乱序、三级必需标题、围栏/引用/列表伪标题和层级溢出继续拒绝。
- 凭据、HTML、绝对 workspace 路径在规范化前后都继续拒绝。
- job 只在 `changed` 时原子写回一次，完成入库的 Markdown、bytes 和 hash 与写回内容一致。
- 不产生第二次 `deliver()` 或任何额外模型调用。

### 页面 RED→GREEN

- 工作总结主面板包含独立 task rail 和 report detail 区域，不再把版本历史放在左栏。
- 任务卡的标题和备注具有截断结构，失败原因来自安全映射。
- 任务卡只保留状态相关直接操作，其余操作通过紧凑菜单触发原有事件。
- 详情操作区具有可换行布局，版本历史位于详情上下文。
- 响应式规则覆盖桌面双列和 960px 以下单列。
- 现有编辑、重试、对话、删除、设为当前版本、导出和实时状态 mounted 测试继续通过。

### 验收门禁

- focused summary/Claude tests 零失败。
- 全量 `npm test` 零失败。
- `npm run build`、`npm run verify:release` 和 `git diff --check` 通过。
- 开发版在桌面与窄窗口完成视觉检查。
- 使用真实 Claude 生成下一版本，不刷新页面即可到达“已完成”，数据库和 workspace 保存规范 Markdown。
- 真实生成通过后再执行 Setup 与 Portable 页面、编辑/删除、预览和导出验收。

## 兼容与回滚

- 旧数据库报告不修改；读取和导出继续兼容原 Markdown。
- 规范化仅作用于新交互式 run 的稳定输出文件。
- 如果规范化出现回归，可回滚纯函数调用和 changed 写回，不需要数据库迁移。
- 页面重构不改变 IPC、store 字段或报告所有权；可独立回滚组件结构和样式。
- 任一真实验收失败时保持发布门禁关闭，不提交最终验收闭环记录。
